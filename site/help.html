Workflow

This site wraps sysmon-modular: a library of small XML modules, one per detection idea or noise exclusion, organised by Sysmon event ID. The same Go code that powers upstream's CLI, compiled to WebAssembly, does the merging, validation and analysis inside your browser. Nothing you select or edit is sent anywhere.

  1. Search for what you want to change: a process name, an ATT&CK ID, a field, a category (cat:22), a module type (kind:exclude). Every hit is the matching <Rule> in context.
  2. Switch modules on or off with the toggle on each hit (or Switch on/off all hits). You start from upstream's standard configuration.
  3. Edit a rule with Edit (form) or XML (raw). Both validate with upstream's validator before saving; upstream files are never changed – your version is stored as an overlay.
  4. Create your own modules for environment-specific exclusions (Save / Load menu → New custom module, or from a category search).
  5. Download (footer, or d): the selected modules are merged into one sysmonconfig.xml; a summary shows findings and a pre-deploy checklist first.
  6. Deploy with sysmon64 -c sysmonconfig.xml – see Deploying.

The standard configuration

You start from sysmon-modular's published sysmonconfig.xml ("Balanced"): every detection and noise-exclusion module except FileDelete archiving (event 23). It is the recommended starting point for workstations and servers. Everything you change – modules switched on or off, edited rules, custom modules – is stored in this browser and applied on top of that standard when you press Download.

Builds follow upstream's release settings: comments are preserved, the analyzer always runs, and events or fields newer than the Sysmon target chosen in the footer are removed so the file loads cleanly. Other upstream variants are one search away: only the exclusions (research), or switch FileDelete on via cat:23. Hosts with Microsoft Defender for Endpoint: upstream's mde_covered_modules.txt lists what MDE already collects – import it as an exclude list from Save / Load if you want the "MDE augment" variant.

Reset to standard configuration (Save / Load menu) restores the standard selection and discards your edited and custom modules – export first if you want to keep them.

Server roles (domain controllers, SQL, Exchange/IIS, RDS…) do not need separate configurations: Sysmon records the same event types on every Windows host and the detection modules apply everywhere. What differs per role is the noise, so add your own exclude modules for the software on those hosts. Role-specific security telemetry (Kerberos, mailbox access, HTTP requests) comes from the Windows Security log and application logs, not from Sysmon.

Sysmon configuration basics

A Sysmon configuration is an XML document. The root carries a schemaversion (the configuration schema, not the binary version); options such as HashAlgorithms sit directly under the root, and all filtering lives under <EventFiltering>.

<Sysmon schemaversion="4.90">
  <HashAlgorithms>*</HashAlgorithms>
  <EventFiltering>
    <RuleGroup name="..." groupRelation="or">
      <ProcessCreate onmatch="include">
        <Rule name="technique_id=T1059.001,technique_name=PowerShell" groupRelation="and">
          <Image condition="image">powershell.exe</Image>
          <CommandLine condition="contains">-enc</CommandLine>
        </Rule>
      </ProcessCreate>
    </RuleGroup>
  </EventFiltering>
</Sysmon>

Inside EventFiltering the hierarchy is: RuleGroup → event filter (one element per event type, e.g. ProcessCreate, with onmatch) → Rule (optional grouping with its own groupRelation) → field conditions (elements named after event fields such as Image or CommandLine). The rule editor mirrors this hierarchy exactly.

Each Sysmon event type has its own filter tag and its own set of fields – DestinationPort exists for NetworkConnect but not for ProcessCreate. The editor only offers the fields valid for the selected event type; the validator rejects the rest (SYS202).

include vs. exclude – which one wins?

＋
onmatch="include"

Allow-list. Only events that match a rule are logged. An include block with no rules therefore logs nothing of that event type – that is the standard way to switch an event type off.

－
onmatch="exclude"

Deny-list. Everything is logged except events that match a rule. An exclude block with no rules logs everything of that event type.

Precedence: exclude always wins. Sysmon evaluates both sets for an event type; if any exclude rule matches, the event is dropped – even if an include rule also matched. This is why sysmon-modular's exclude modules are safe to add for noise reduction (they can only ever remove events) and why you should keep them narrow: an exclusion that matches too broadly silently blinds the detections in the include modules.

The sysmon-modular convention: include modules describe detections (things you want to see, tagged with ATT&CK techniques), exclude modules describe known-good noise (a specific product, an update agent, …).

Event types that have no filter block at all fall back to Sysmon's built-in defaults, which differ per event (process creation is on, network connections and image loads are off). Do not rely on that: every category in sysmon-modular declares its filters explicitly, and the merged file is what determines behaviour.

How rules match

  • Bare conditions directly under an event filter (no Rule wrapper) follow Sysmon's classic combination: conditions on the same field are OR-ed, conditions on different fields are AND-ed – unless the enclosing RuleGroup sets groupRelation, which then applies to all of them.
  • <Rule groupRelation="and"> groups several conditions into one match: all of them must be true (and) or any of them (or). This is how "PowerShell and command line contains -enc" is expressed. Nearly every sysmon-modular module uses Rule elements with and.
  • RuleGroup groupRelation="or" (the default in sysmon-modular) means: the event matches the group if any rule or bare condition inside it matches. Several groups for the same event type and onmatch are all evaluated; a match in any group counts.
  • name attributes on a Rule or a condition are copied into the event's RuleName field, so you can see in the log which rule fired. sysmon-modular encodes MITRE ATT&CK metadata there: technique_id=T1059.001,technique_name=PowerShell. The validator checks that the ID exists and the name matches.
  • Matching is case-insensitive. Multi-value operators (is any, contains any/all, excludes any/all) take a ;-separated list; a ; in the value of any other operator is an error (SYS107).

How sysmon-modular merges

Every module is a complete mini-configuration with one or more RuleGroups. sysmon-modular merge takes the template (templates/sysmon_template.xml: root options such as hashing and DNS lookup), drops all selected modules' RuleGroups into EventFiltering unchanged, sets schemaversion for the target Sysmon version and validates the result. It does not rewrite or deduplicate rules – what you see in a module is what ends up in the file.

The order of modules is not significant for the outcome, because Sysmon evaluates all groups and applies the exclude-wins rule globally per event type.

The download runs the merge with --analyze, which adds conflict findings (an include and an exclude that cancel each other), performance findings (patterns that are expensive to evaluate on every event) and recommendations (e.g. an exclusion by bare image name where a full path would be safer). Recommendations never fail a build; errors do.

Sysmon versions & schema

The Sysmon target in the footer decides the schemaversion written to the output and which events and fields are allowed. Newer events (e.g. FileExecutableDetected, Sysmon 15) and fields (e.g. User on file events, Sysmon 14) are removed for an older target (reported as SYS204/SYS205 warnings in the download summary) so the file loads on that binary.

A module's own schemaversion only matters for the module file itself; the merged file always uses the Sysmon target from the footer. The rule editor sets it automatically to the lowest schema that supports the events the module uses, so you never need to touch it (the raw XML editor still lets you). sysmon64 -s prints the schema of an installed binary if you need to check which fields it knows.

What each event type costs

Independent of which modules you pick, switching an event type on has an inherent cost on every host. The sidebar tags (high volume, cpu, disk, privacy) and the strip on each category page summarise it; hover for the reason. The main levers:

  • Hashing – the template sets HashAlgorithms to * (MD5 + SHA1 + SHA256 + IMPHASH). Every ProcessCreate, DriverLoad, ImageLoad, FileDelete/FileDeleteDetected, FileCreateStreamHash and FileExecutableDetected event hashes a file. Fine for processes; expensive when ImageLoad is broad.
  • ImageLoad (7) – every DLL load is hashed and signature-verified. The single most CPU-expensive event type; only viable with tight include rules.
  • ProcessAccess (10) – a call-stack trace is generated per event, and the events are very frequent. Keep it focused on lsass.exe & co.
  • RawAccessRead (9) – sector-level reads. Backup, AV and defrag issue thousands per second; upstream ships it off (empty include filter). Enable only where no process should read raw disk, e.g. domain controllers, with exclusions for backup/AV.
  • FileDelete (23) – deleted files are hashed and copied into the archive directory; disk grows without rotation. ClipboardChange (24) also writes clipboard text to the archive – a privacy decision.
  • Volume – NetworkConnect, DnsQuery, FileCreate and Registry events are cheap each but numerous; the cost lands in the event log and the forwarder (WEC/agent), and in your SIEM licence.
  • Template options – CheckRevocation (online revocation checks per signature) and DnsLookup (reverse DNS per connection) are off in upstream's template and cannot be changed here; leave them off unless you know why.

Search syntax

The start page searches the selected modules (or all – the toggle next to the box) as you type; module type and category are part of the query (kind:, cat:) rather than separate controls. Plain words are AND-ed and matched case-insensitively against module path, RuleGroup name, event, rule name, fields, operators and values. Each hit is the matching <Rule> or bare condition; a module whose only match is its name is shown once in full.

Deploying

  1. Download sysmonconfig.xml (footer button) and copy it next to sysmon64.exe on a pilot host. Keep every file you deploy – it is what you roll back to.
  2. Install (first time on a host): sysmon64.exe -accepteula -i sysmonconfig.xml
  3. Update an existing installation (no reboot, no reinstall): sysmon64.exe -c sysmonconfig.xml
  4. Verify – dump the active configuration and check schema version and rule counts: sysmon64.exe -c. Events land in Applications and Services Logs → Microsoft → Windows → Sysmon → Operational; event 16 confirms the configuration change.
  5. Watch volume for a day on the pilot group, then roll out. Add exclusions for your own noisy software as custom exclude modules and download again.
  6. Roll back by applying an earlier file with -c, or reset to Sysmon's defaults: sysmon64.exe -c --

The hosts must run the Sysmon major version chosen in the footer or newer – an older binary rejects the file with a schema error. Distribute sysmon64.exe and the XML with your management tool (GPO startup script or scheduled task, Intune Win32 app / remediation, SCCM package), run the update command as SYSTEM; Sysmon re-reads the configuration without a reboot.

Practical tips

  • Start from the standard, then subtract. You begin with upstream's published sysmonconfig.xml. Switch off what does not apply (products you do not run) and add exclusions for your own noise.
  • Write exclusions as narrowly as possible: full path (begin with C:\Program Files\Vendor\) plus, where possible, a second field such as ParentImage or DestinationPort. Exclude wins, so a broad exclusion is the easiest way to lose detections.
  • Noisy event types: ImageLoad (7), ProcessAccess (10), RegistryEvent (12–14) and FileCreate (11) can produce very high volumes. Keep their include modules focused and test on a few hosts first.
  • Keep the ATT&CK metadata in rule names when you add detections; the coverage report and Navigator layer are generated from it.
  • Different fleets, different files (servers vs. workstations, Sysmon 13 hosts vs. Sysmon 15 hosts): export your changes as JSON per fleet and import the one you are working on.
  • Compare before deploying: the Diff tab on a build shows which rules and techniques changed compared with the previous build, ignoring pure formatting.

Where the data lives

Everything stays in your browser: your selection and edited/custom modules in localStorage. Nothing is uploaded – the site is static files and a WebAssembly engine. That also means clearing site data, private windows or another device start from scratch.

Use Save / Load (footer) to export one JSON file with your selection and edited modules, and import it again anywhere – that file is the thing to keep in your own repository.

The export references upstream modules by path, so it stays valid across upstream updates; modules that disappear upstream are dropped on import, and modules you edited keep your version until you reset them.
